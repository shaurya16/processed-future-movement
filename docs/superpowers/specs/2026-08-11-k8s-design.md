# Design: `k8s` — Kubernetes manifests for the full stack

Status: Approved
Branch: `feature/k8s`

## Context

Fifth buildable slice of processed-future-movement, following `common`,
`ingestion-service`, `processing-service`, and `frontend` (see
[2026-08-11-frontend-design.md](2026-08-11-frontend-design.md)). Per the chosen
architecture (see [README.md](../../../README.md)):

```
Input.txt --> ingestion-service --> Kafka topic --> processing-service --> REST API --> frontend
                                                          (Kafka Streams          (Angular)
                                                           aggregation)
```

`k8s` deploys the whole stack — Kafka, `ingestion-service`, `processing-service`, and
`frontend` — to a local Kubernetes cluster (kind/minikube). No Dockerfiles exist yet for
any component, so building them is part of this slice.

**The open problem this design exists to solve:** `processing-service`'s Kafka Streams
topology declares `future-transactions` as a source topic but never creates it (only
`ingestion-service` does, via its own `NewTopic` bean in
`ingestion-service/src/main/java/com/pfm/ingestion/kafka/KafkaTopicConfig.java`). If
`processing-service` starts against a fresh broker before that topic exists, Kafka
Streams' topology validation throws a fatal `MissingSourceTopicException` that
permanently kills the `StreamThread` with no self-recovery — `GET /api/report` then
returns `503` forever, not just until the topic shows up. This must be fixed by
sequencing pod startup at the k8s level, not by changing application code (specifically,
not by mirroring `ingestion-service`'s `NewTopic` bean into `processing-service` — that
was considered and explicitly rejected in favor of a k8s-only fix, see Decision 1).

## Decisions made during brainstorming

1. **Ordering-bug fix — `initContainer` on `processing-service` polling Kafka directly
   for the topic, not an application-code change.** The `processing-service` pod spec
   gets an `initContainer` (reusing the `apache/kafka:3.9.2` image, already pulled for
   the broker itself) that loops `kafka-topics.sh --bootstrap-server kafka:9092 --list`
   until `future-transactions` appears, then exits so the main container starts.
   - **Why k8s-level, not a mirrored `NewTopic` bean in `processing-service`**: an
     idempotent bean in both services was considered (whichever pod starts first creates
     the topic, the other no-ops) but explicitly rejected — this slice's constraint is to
     fix the bug through deployment sequencing, keeping `processing-service` unaware of
     topic provisioning, consistent with `ingestion-service` remaining the sole owner of
     topic creation.
   - **Why poll Kafka directly, not wait on `ingestion-service`'s readiness as a proxy**:
     checks the actual precondition (topic exists on the broker) instead of an indirect
     signal. Correct on first cluster bring-up regardless of pod scheduling order, and
     still correct if `processing-service` restarts independently later (e.g. a node
     reschedule) since the check re-runs every pod start, not just once.
2. **Health probes — add `spring-boot-starter-actuator` to both backend services.**
   Neither service has a health endpoint today. This is the one application-code change
   in this slice, scoped as purely additive infrastructure (dependency + minimal
   config), not business logic — distinct from the rejected `NewTopic`-bean approach to
   the ordering bug.
   - **`ingestion-service`**: default actuator behavior is sufficient
     (`/actuator/health/liveness` + `/readiness` reflecting Spring context state) — no
     ongoing internal state to reflect beyond "is the app up."
   - **`processing-service`**: default actuator behavior alone isn't meaningful enough —
     Kafka Streams can leave a dead `StreamThread` while the Spring context otherwise
     looks healthy. A small custom `HealthIndicator` reads `KafkaStreams.state()` via the
     injected `StreamsBuilderFactoryBean` (`RUNNING`/rebalancing → up, anything else →
     down), wired to `/actuator/health/readiness`. This mirrors the service's own
     existing "not `RUNNING` → `503`" logic for `/api/report` (processing-service design
     decision 10), just surfaced to k8s so a broken pod stops receiving traffic instead
     of serving `503`s indefinitely.
3. **Manifest tooling — plain YAML, no Kustomize/Helm.** One target environment (local
   kind/minikube), so templating/overlays are YAGNI. Matches this project's established
   minimal-dependency pattern (hand-rolled CSV instead of a library, JSON instead of
   Avro+Schema Registry, etc).
4. **Manifest layout — one file per component, each bundling its Deployment + Service.**
   `k8s/namespace.yaml`, `k8s/kafka.yaml`, `k8s/ingestion-service.yaml`,
   `k8s/processing-service.yaml`, `k8s/frontend.yaml`. Applied via `kubectl apply -f
   k8s/`. All resources in a dedicated `pfm` namespace — keeps `kubectl get` output
   scoped and lets the whole stack be torn down with one `kubectl delete namespace pfm`.
5. **Configuration — plain env vars on each container spec, no ConfigMaps.** Small,
   fixed set of values per service (mirrors `docker-compose.yml`'s existing style); a
   ConfigMap would be indirection without benefit at this scale.
6. **Image strategy — local build + `kind load docker-image`, no registry.** Scoped to
   local kind/minikube only (not cloud-portable) per this slice's target environment.
   Images tagged locally (e.g. `pfm/ingestion-service:local`),
   `imagePullPolicy: IfNotPresent`, loaded directly into the cluster — no registry to
   stand up or push credentials to manage for a local demo.
7. **`ingestion-service` and `processing-service` Dockerfiles — multi-stage Maven
   build, built from the repo root.** Build stage: `maven:3.9-eclipse-temurin-21` runs
   `mvn -pl <module> -am -DskipTests package` (the `-am` flag is required since both
   modules depend on `common`, an unpublished sibling module — the build context must be
   the repo root, not the module directory, so this Maven invocation can see `common`'s
   sources). Runtime stage: `eclipse-temurin:21-jre-alpine`, copies the `-exec.jar`
   (spring-boot-maven-plugin's `classifier: exec`, already configured in both pom.xml
   files), `ENTRYPOINT ["java","-jar","app.jar"]`.
   - **`ingestion-service`'s Dockerfile additionally `COPY`s `sample-data/`** into the
     image so its default `INGESTION_FILE_PATH=sample-data/Input.txt` resolves inside
     the container against `WORKDIR /app` with no code or config change — the k8s
     manifest doesn't override `INGESTION_FILE_PATH`.
8. **`frontend` Dockerfile — multi-stage Node build + nginx runtime, reverse-proxying
   `/api`.** Build stage: `node:22-alpine` runs `npm ci && npm run build`, producing
   `dist/frontend/browser` (Angular 21's default output layout, confirmed via a local
   build). Runtime stage: `nginx:alpine`, copies the build output to
   `/usr/share/nginx/html`, with a custom `nginx.conf` serving the SPA (`try_files $uri
   /index.html`) and reverse-proxying `/api/` to
   `http://processing-service.pfm.svc.cluster.local:8082/api/`.
   - **Why reverse-proxy at the nginx layer, not have the Angular app call
     `processing-service` directly**: mirrors the dev-time `proxy.conf.json` model the
     frontend design already anticipated (frontend design decision 2's "shared
     origin/reverse proxy" note) — the app's existing relative `/api/*` calls work
     unchanged, and `processing-service` still needs no CORS configuration in
     production either.
9. **Kafka manifest — single-broker KRaft `Deployment`, simplified from
   `docker-compose.yml`.** `replicas: 1` (Kafka itself isn't clustered in this project
   either way), image `apache/kafka:3.9.2`, `emptyDir` volume for
   `/tmp/kraft-combined-logs` (ephemeral — matches docker-compose's own non-persistent
   storage; acceptable for a local demo where data loss on pod restart is already the
   status quo). Only one listener is configured (`PLAINTEXT://:9092`), simplified from
   docker-compose's dual-listener (`PLAINTEXT_HOST` + `PLAINTEXT`) setup, because that
   split existed to serve both host-machine clients and container-network clients — in
   k8s every client is an in-cluster pod reaching Kafka via the `Service` DNS name
   (`kafka.pfm.svc.cluster.local:9092`, short form `kafka:9092` within the namespace), so
   there's no split-brain to configure around. `Service` is `ClusterIP` — nothing outside
   the cluster talks to Kafka directly.
10. **`ingestion-service` and `processing-service` — `replicas: 1`, `ClusterIP`
    Services.** Required by each service's own design doc, not a new constraint:
    `ingestion-service`'s file-ingestion idempotency cache is in-process only;
    `processing-service`'s Interactive Queries need one instance owning all state-store
    partitions. Both stay internal (`ClusterIP`) — nothing outside the cluster needs
    direct access; `ingestion-service`'s `POST /api/ingest` is triggered manually via
    `kubectl port-forward` + `curl` for a demo, consistent with its existing
    REST-triggered design (no directory watcher, no Job wrapping it).
11. **`frontend` — `NodePort` Service, fixed `nodePort: 30080`.** Simplest external
    access for a local kind/minikube demo — no ingress controller to install/configure.
    A fixed port gives a predictable local URL (`http://localhost:30080` via kind's
    default port mapping, or `kubectl port-forward` as a fallback).
    - **Rejected: Ingress.** More production-like, but requires installing and
      documenting an ingress controller as a prerequisite for a cluster this project
      doesn't otherwise need one for.
12. **CI workflow — bundled into this slice, not a separate follow-up.** Adds
    `.github/workflows/ci.yml`: one job running `mvn -B clean verify` from the repo root
    (builds `common` → `ingestion-service` → `processing-service` in module order, runs
    unit + Testcontainers integration tests — GitHub-hosted runners ship Docker
    preinstalled, so Testcontainers works with no extra setup), and a second job for
    `frontend/` running `npm ci`, `npm test`, `npm run build`. Triggered on push/PR.
    Closes the gap flagged during `processing-service`'s and `frontend`'s final reviews
    (no clean-build verification existed; a real build break was once invisible without
    one). Bundled here because this slice already introduces the Docker/build artifacts
    for every service — natural to verify the same build paths in CI at the same time,
    rather than opening a second unrelated branch just for that.
13. **Validation — a real throwaway kind cluster, not manifest inspection alone.**
    docker, kind, and kubectl are all available locally, so this slice's implementation
    work includes actually standing up a kind cluster, building and loading all three
    images, applying the manifests, and proving the ordering-bug fix works against a
    **fresh** cluster (no topic pre-existing) rather than asserting it by reading the
    YAML. See Testing section.

## Components

**New files:**
- `k8s/namespace.yaml` — `pfm` namespace. **Correction discovered during final review**:
  renamed to `k8s/00-namespace.yaml` — `kubectl apply -f k8s/` applies files in
  filename-alphabetical order with no dependency awareness, and `namespace.yaml` sorted
  after `frontend.yaml`, `ingestion-service.yaml`, and `kafka.yaml`, so those three failed
  with `NotFound: namespaces "pfm"` on a fresh cluster's first apply. The `00-` prefix
  guarantees the namespace is created first in a single `kubectl apply -f k8s/` pass.
- `k8s/kafka.yaml` — `Deployment` (KRaft single-broker, `emptyDir`) + `ClusterIP Service`.
- `k8s/ingestion-service.yaml` — `Deployment` (`replicas: 1`, liveness/readiness probes
  against actuator) + `ClusterIP Service` (port 8081).
- `k8s/processing-service.yaml` — `Deployment` (`replicas: 1`, `initContainer` polling
  Kafka for the topic, liveness/readiness probes against actuator) + `ClusterIP Service`
  (port 8082).
- `k8s/frontend.yaml` — `Deployment` (`replicas: 1`) + `NodePort Service`
  (`nodePort: 30080`).
- `ingestion-service/Dockerfile`, `processing-service/Dockerfile`, `frontend/Dockerfile`.
- `frontend/nginx.conf` — SPA fallback + `/api` reverse proxy to `processing-service`.
- `.github/workflows/ci.yml`.

**Modified files:**
- `ingestion-service/pom.xml`, `processing-service/pom.xml` — add
  `spring-boot-starter-actuator`; `application.yml` in both — expose
  `health.probes.enabled` liveness/readiness groups.
- `processing-service` — new `KafkaStreamsHealthIndicator` (or equivalent
  `HealthIndicator`/`HealthContributor`) reading `KafkaStreams.state()` via the existing
  `StreamsBuilderFactoryBean`.

## Data flow (deployment / startup)

1. `kubectl apply -f k8s/` creates the `pfm` namespace and all four components.
2. Kafka's pod starts, KRaft single-node broker becomes ready (no topics yet on a fresh
   cluster).
3. `ingestion-service`'s pod starts; its Spring context boot creates `future-transactions`
   via its existing `NewTopic` bean, independent of whether `POST /api/ingest` has ever
   been called.
4. `processing-service`'s pod is scheduled; its `initContainer` polls Kafka directly for
   `future-transactions` and blocks until it exists (regardless of whether step 3 has
   completed yet — this is what makes the fix order-independent, not just "usually fast
   enough"). Once the topic is visible, the main container starts, Kafka Streams'
   topology validation succeeds, and the `StreamThread` reaches `RUNNING`.
5. `frontend`'s pod starts, serving the Angular build via nginx and reverse-proxying
   `/api/*` to `processing-service`.
6. A demo operator port-forwards `ingestion-service` and `POST`s `/api/ingest` to
   publish the sample data; the frontend, reachable at `localhost:30080`, polls
   `GET /api/report` (per the frontend's existing `503`-retry design) until Kafka
   Streams' state store is populated, then renders the table.

## Testing

- **Unit**: `processing-service`'s new Kafka-Streams-state `HealthIndicator` — `RUNNING`
  (and rebalancing) states report up; other states (`ERROR`, `PENDING_SHUTDOWN`,
  `NOT_RUNNING`) report down.
- **Live smoke test** (kind cluster, created and torn down as part of this slice's
  implementation work, not left running):
  1. Build all three images; `kind load docker-image` each into a fresh kind cluster.
  2. `kubectl apply -f k8s/` against that fresh cluster (no `future-transactions` topic
     exists yet at this point).
  3. Confirm `processing-service`'s pod shows `Init:0/1` (blocked in its initContainer)
     immediately after apply, then transitions to `Running`/`Ready` once
     `ingestion-service` has created the topic — this is the actual proof the
     ordering-bug fix works, not an inference from reading the YAML.
  4. Port-forward `ingestion-service`, `POST /api/ingest`.
  5. Port-forward or hit `localhost:30080` (frontend NodePort); confirm the report table
     renders and matches `sample-output/Output.csv`.
  6. `kubectl get pods -n pfm` shows all four components `Running`/`Ready` with no
     restarts/crash-loops.
  7. Tear down the kind cluster.
- **CI**: the new `.github/workflows/ci.yml` itself is validated by observing it run
  (and pass) on the PR this slice produces.

## Out of scope for this slice

- Cloud-portable manifests (registry push, Ingress controller, resource limits tuned for
  multi-tenant nodes) — this slice targets local kind/minikube only per its scoping
  decision.
- Kustomize/Helm — YAGNI with a single target environment (Decision 3).
- Automating `POST /api/ingest` (e.g. a Job or init trigger) — stays a manual demo step,
  consistent with `ingestion-service`'s existing REST-triggered design.
- Persistent storage / StatefulSet for Kafka — `emptyDir` is an accepted, documented
  limitation matching docker-compose's existing ephemeral behavior (Decision 9).
- TLS, authentication/authorization on any component — no such requirement has been
  raised for this project at any prior slice.
- CI deploying to any cluster (real or kind) — `ci.yml` only builds/tests; it does not
  `kubectl apply` anywhere.
