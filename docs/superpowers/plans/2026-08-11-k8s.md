# k8s Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deploy the full processed-future-movement stack (Kafka, ingestion-service, processing-service, frontend) to a local Kubernetes cluster, fixing processing-service's Kafka Streams startup-ordering bug at the k8s level and adding a CI build-verification workflow.

**Architecture:** Three new multi-stage Dockerfiles (two Spring Boot services built from the repo root via Maven reactor, one Angular app built with Node then served by nginx) feed four plain-YAML k8s manifests (Kafka, ingestion-service, processing-service, frontend) applied to a `pfm` namespace on a local kind/minikube cluster. `processing-service`'s pod gets an `initContainer` that polls Kafka directly for the `future-transactions` topic before its main container starts — the k8s-level fix for the ordering bug, with no application-code change to `processing-service`'s topic handling. Both backend services gain Spring Boot Actuator for liveness/readiness probes; `processing-service` additionally gets a small custom `HealthIndicator` reflecting real Kafka Streams state, wired into its actuator readiness group.

**Tech Stack:** Docker multi-stage builds, `apache/kafka:3.9.2` (KRaft single-broker), `eclipse-temurin:21-jre-alpine` (ingestion-service) / `eclipse-temurin:21-jre` (processing-service, glibc required for RocksDB), `node:22-alpine` + `nginx:alpine`, plain Kubernetes YAML manifests, `kind`, GitHub Actions.

## Global Constraints

- Java 21 (`maven.compiler.release` / `java.version` in existing poms) — do not change.
- Spring Boot 3.5.4 parent (existing) — do not change.
- Node engine `^22.12.0` (from `@angular/cli`'s `package.json` `engines.node`) — use `node:22-alpine` for the frontend build stage.
- All new k8s resources live in namespace `pfm`.
- `ingestion-service` and `processing-service` Deployments: `replicas: 1` (required by their own design docs — in-process idempotency cache and single-instance Interactive Queries respectively). `kafka` Deployment: `replicas: 1` (single-broker KRaft, not clustered).
- Service ports: `kafka` 9092, `ingestion-service` 8081, `processing-service` 8082, `frontend` 80 (NodePort `30080`).
- Local image tags: `pfm/ingestion-service:local`, `pfm/processing-service:local`, `pfm/frontend:local`, `imagePullPolicy: IfNotPresent`, loaded into the cluster via `kind load docker-image` — no registry.
- The ordering-bug fix must be k8s-manifest-only: no `NewTopic` bean (or equivalent) added to `processing-service`.
- The only application-code changes in this plan are additive Actuator wiring (Tasks 1-2) — no existing business logic is modified.

```java
package com.pfm.processing.streams;

import org.apache.kafka.streams.KafkaStreams;
import org.springframework.boot.actuate.health.Health;
import org.springframework.boot.actuate.health.HealthIndicator;
import org.springframework.kafka.config.StreamsBuilderFactoryBean;
import org.springframework.stereotype.Component;

@Component
public class KafkaStreamsHealthIndicator implements HealthIndicator {

    private final StreamsBuilderFactoryBean streamsBuilderFactoryBean;

    public KafkaStreamsHealthIndicator(StreamsBuilderFactoryBean streamsBuilderFactoryBean) {
        this.streamsBuilderFactoryBean = streamsBuilderFactoryBean;
    }

    @Override
    public Health health() {
        KafkaStreams kafkaStreams = streamsBuilderFactoryBean.getKafkaStreams();
        if (kafkaStreams == null) {
            return Health.down().withDetail("state", "NOT_STARTED").build();
        }

        KafkaStreams.State state = kafkaStreams.state();
        if (state.isRunningOrRebalancing()) {
            return Health.up().withDetail("state", state.name()).build();
        }
        return Health.down().withDetail("state", state.name()).build();
    }
}
```

This mirrors `ReportService`'s own not-ready check (`processing-service/src/main/java/com/pfm/processing/report/ReportService.java:27-30`) — same `StreamsBuilderFactoryBean` injection, same `KafkaStreams.State` check.

### Task 5: `frontend/Dockerfile` + `frontend/nginx.conf.template`

**Correction discovered during this task's implementation** (superseding the original file content below, which the first implementation attempt found doesn't actually work — verified empirically by the controller against a real `nginx:alpine` container before this correction was written): a static `proxy_pass http://processing-service:8082/api/;` makes nginx resolve that hostname **once, at config-load time**. Since `processing-service` won't be resolvable when this image is smoke-tested standalone (no such container/Service exists yet), nginx fails with `host not found in upstream "processing-service"` and **the whole container exits — `index.html` stops being served too, not just `/api/`.** The fix is *not* simply switching to a variable-based `proxy_pass` (e.g. `set $upstream http://processing-service:8082; proxy_pass $upstream/api/;`) either — that defers resolution to request time, but nginx then needs an explicit `resolver` directive to do that lookup at all; without one, every `/api/` request permanently 502s with `no resolver defined`, in standalone Docker **and** in the real k8s deployment alike, regardless of whether `processing-service` actually exists. The correct, verified fix uses nginx's official image's built-in local-resolver auto-detection (confirmed present in this project's `nginx:alpine` image, version 1.31.3): opt in via `NGINX_ENTRYPOINT_LOCAL_RESOLVERS=1`, and reference the resolver list the entrypoint computes from `/etc/resolv.conf` — `${NGINX_LOCAL_RESOLVERS}` (note: **not** `${NGINX_ENTRYPOINT_LOCAL_RESOLVERS}`, which is only the opt-in trigger name, not the computed value) — via the image's template mechanism (files under `/etc/nginx/templates/*.template` get `envsubst`'d into `/etc/nginx/conf.d/` at container start). This works correctly both standalone (Docker's embedded DNS at `127.0.0.11`) and in real k8s (the pod's `/etc/resolv.conf` points at the cluster's CoreDNS), with no hardcoded IP.

- [ ] **Step 1: Write nginx.conf.template**

Create `frontend/nginx.conf.template`:

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;
    resolver ${NGINX_LOCAL_RESOLVERS};

    location /api/ {
        set $upstream http://processing-service:8082;
        proxy_pass $upstream/api/;
        proxy_set_header Host $host;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

### Task 8: `k8s/processing-service.yaml` — the ordering-bug fix

**Files:**
- Create: `k8s/processing-service.yaml`

**Interfaces:**
- Consumes: image `pfm/processing-service:local` (Task 4), `/actuator/health/liveness` + `/readiness` (Task 2), Kafka Service `kafka:9092` (Task 6).
- Produces: `processing-service` reachable in-cluster at `processing-service:8082`, only after its `initContainer` confirms the `future-transactions` topic exists. Consumed by Task 9 (frontend's nginx proxy target) and Task 11 (live smoke test — this is the manifest whose behavior proves the ordering-bug fix).

- [ ] **Step 1: Write the manifest**

Create `k8s/processing-service.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: processing-service
  namespace: pfm
  labels:
    app: processing-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: processing-service
  template:
    metadata:
      labels:
        app: processing-service
    spec:
      initContainers:
        - name: wait-for-topic
          image: apache/kafka:3.9.2
          command:
            - sh
            - -c
            - |
              until /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka:9092 --list | grep -qx future-transactions; do
                echo "waiting for future-transactions topic..."
                sleep 2
              done
              echo "future-transactions topic found, starting processing-service"
      containers:
        - name: processing-service
          image: pfm/processing-service:local
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8082
          env:
            - name: KAFKA_BOOTSTRAP_SERVERS
              value: "kafka:9092"
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8082
            initialDelaySeconds: 15
            periodSeconds: 10
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8082
            initialDelaySeconds: 10
            periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata:
  name: processing-service
  namespace: pfm
spec:
  selector:
    app: processing-service
  ports:
    - port: 8082
      targetPort: 8082
```

**Correction discovered during this task's implementation** (superseding the original claim below, which was wrong — traced to the controller misreading a multi-command shell chain's output during design, and never independently re-verified before now): `kafka-topics.sh` is **NOT** on `PATH` inside `apache/kafka:3.9.2` — confirmed directly (`command -v kafka-topics.sh` exits 127, "not found"; the image's actual `PATH` is `/opt/java/openjdk/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`, which does not include `/opt/kafka/bin`). The script only works with kafka-topics.sh's **absolute path**, `/opt/kafka/bin/kafka-topics.sh` (confirmed present and executable there, and `/opt/kafka/bin/kafka-topics.sh --version` correctly prints `3.9.2`). A bare `kafka-topics.sh` invocation fails with `sh: kafka-topics.sh: not found` (exit 127); piped into `grep -qx future-transactions` against empty stdin, `grep` exits 1 (no match) — so the `until` loop's condition is always false and it retries forever, **even after the topic genuinely exists on the broker**. That failure mode is worse than the bug this task fixes: instead of a fatal-but-diagnosable exception, the pod would sit in `Init:0/1` permanently. This is the ordering-bug fix: `processing-service`'s main container cannot start until this loop exits, which only happens once the topic genuinely exists on the broker, regardless of whether `ingestion-service`'s pod happened to start first — but only once the command above actually invokes the real binary via its absolute path.

Run: `kubectl apply --dry-run=client -f k8s/processing-service.yaml`
Expected: `deployment.apps/processing-service created (dry run)` and `service/processing-service created (dry run)`, no errors.
